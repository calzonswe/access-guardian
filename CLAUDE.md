## Project

Access Guardian: an RBAC system for managing access applications to facilities and areas. React/Vite frontend → Express backend → PostgreSQL. Originally generated by Lovable; commits auto-sync with lovable.dev, so keep changes compatible with that workflow (don't restructure the project layout or the Vite config).

UI text, error messages, docs and commit messages are in **Swedish** — follow that for user-facing strings (e.g. backend errors like `'Otillräckliga rättigheter'`).

## Architecture

### Frontend data layer — dual mode (important)

Pages do **not** call the API directly and React Query is effectively unused (only the provider in `App.tsx`). Instead:

- `src/services/api.ts` — thin fetch client (`/api` or `VITE_API_URL`), JWT stored in localStorage `rbac_token`, 401 triggers the handler registered by `AuthContext`.
- `src/services/dataStore.ts` — the facade every page uses. On load it probes `/api/health`; if it returns JSON `{status:'ok'}` it runs in **API mode** (loads everything into in-memory caches, sync getters like `getUsers()` read the cache, async mutations call the API), otherwise it falls back to **localStorage mode** (full local CRUD with a seeded admin `admin@company.local`, used by Lovable preview).
- `src/hooks/useDataRefresh.ts` — pages call this to await init + `refreshAll()`, and call `reload()` after mutations to re-fetch and re-render.

Consequences: any new data feature must be implemented in **both** branches of `dataStore.ts` (API + localStorage), plus a function in `api.ts`. Paged lists (`fetchUsersPage`, `fetchApplicationsPage`) use server-side pagination in API mode and filter in memory locally. Plain `npm run dev` has no `/api` proxy, so it runs in localStorage mode.

Auth/session lives in `src/context/AuthContext.tsx`; page access per role is enforced by `RoleGuard` routes in `src/App.tsx`. Domain types are in `src/types/rbac.ts` and `src/types/organization.ts`. `src/components/ui/` is generated shadcn-ui.

### Backend (`backend/src/`, plain ESM JavaScript)

- `index.js` mounts all routers under `/api/*`; everything except `/api/auth` and `/api/contractor` (public contractor application flow, 20 req/h) goes through `authMiddleware`. A global rate limit applies to `/api/`. Admin endpoints `/api/admin/run-expiry-job` and `/api/admin/system-status` are defined inline.
- `middleware/rbac.js` — `requireRole(...)`, `requireFacilityAccess(getId)`, `requireAreaAccess(getId)` and helpers (`isManagerOf`, `isFacilityAdminOrOwner`, ...). `administrator` bypasses facility/area checks; facility_owner/facility_admin must be linked via `facility_admins`.
- `services/` — `audit.js` (system_logs), `email.js` (nodemailer, disabled when `SMTP_HOST` empty), `settings.js` (`system_settings` table), `areaTree.js` (area hierarchy), `aiGateway.js` (Lovable AI Gateway for audit-log analysis, enabled by `LOVABLE_API_KEY`), `captcha.js`, `loginAttempts.js`, `logger.js`.
- `jobs/expiryJob.js` — interval job (`EXPIRY_JOB_INTERVAL_MS`, default 1h) that expires access/requirements.
- Attachments: `POST /api/attachments` (base64 JSON, legacy) and `POST /api/attachments/multipart` (multer); files stored in `UPLOAD_DIR`.

### Database

- `db/init.sql` — base schema + seed, only run by Docker on first creation of the Postgres volume.
- `db/migrations/NNNN_name.sql` — applied automatically at backend startup by `backend/src/migrations.js` (sorted, each in a transaction, tracked in `schema_migrations`). **Schema changes go in a new numbered migration file**, not only in `init.sql` (existing databases never re-run init.sql). Migrations must be safe on top of a fresh init.sql.
- `db/least-privilege.sql` — optional DB role hardening.

### Domain workflow

Application status: `draft` → `pending_manager` (the applicant's manager or sponsor approves; never the applicant) → `pending_facility` (owner/admin of *that* facility approves) → `approved` → `expired` (revoked by facility staff or the expiry job). Applications with missing requirements (`has_exception`) go from the manager to `pending_exception` and are decided by the facility owner. Administrators may perform any listed transition. The rules are the `TRANSITIONS` table in `backend/src/routes/applications.js` (tested in `backend/test/`); the UI in `ApplicationDetailDialog.tsx` mirrors them.

In API mode the backend writes the audit log and sends notifications for every mutation; `store.addLog` and `notifyApplicationStatusChange` are no-ops there (they only simulate this in localStorage mode). Roles: `administrator`, `facility_owner`, `facility_admin`, `line_manager`, `employee`, `contractor`.

### Deployment

`docker-compose.yml`: `db` (postgres:16) → `backend` (migrations bind-mounted read-only at `/app/migrations`) → `frontend` (nginx serving the Vite build, proxying `/api` to backend, CSP from `nginx.conf.template`).

## Conventions

- Path alias `@/*` → `src/*`.
- TypeScript is deliberately relaxed (`noImplicitAny`, `strictNullChecks`, `noUnusedLocals` off) — don't tighten without asking.
- ESLint: `no-unused-vars` off; `react-refresh/only-export-components` is a warning.
- Backend has no TypeScript and no build step; `backend/` has its own `package.json`.
- `roadmap.md` tracks planned and completed features as a checkbox list.
